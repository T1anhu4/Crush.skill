# Crush：产品、行为系统与界面重新审视

审视日期：2026-09-07。代码基线：`5379820`，本地分支 `codex/v3-living-mind`。

本轮为诊断和设计建议，未修复或发布运行时代码。使用合成数据、临时数据库和模拟网络响应，不使用真实私人聊天或真实模型密钥。结论区分实际复现、静态发现和待验证假设。

## 1. 产品决策

建议保留“关系飞行模拟器”的定位，把普通用户的主要入口改为 GUI。对外产品名可以显示为 **Crush**，Agent 集成继续叫 **Crush.skill**，仓库不必为此改名。

产品承诺：**在一段会持续变化的虚构关系中，练习表达、理解信号、处理不确定性和尊重边界。**

主用户是缺少关系实践、想更自然表达和减少误判的成年人。陪伴体验提供进入和持续体验的理由；练习与复盘提供可迁移的价值。不要把首屏同时卖成恋爱军师、真人克隆、人格检测、AI 女友和 agent 框架。

当前最大的产品矛盾：一边要求用户像真实聊天一样投入，一边每轮展示风险、需求感、下一句攻略。这会让用户优化分数、照抄答案，甚至把正常休息理解成关系失分。

推荐三个明确入口：

| 入口 | 用户任务 | 主要呈现 |
|---|---|---|
| 邂逅 | 和一个有自身节奏的虚构角色相处 | 聊天、媒体、约定、跨日连续性；默认不显示分数 |
| 练习 | 针对邀约、拒绝、误解、修复做一次练习 | 明确场景、短轮次、结束反馈、替代尝试 |
| 复盘 | 看懂证据、不同解释和自己的选择 | 引用原话、时间线、假设与事实分开；不改变角色关系状态 |

聊天记录导入移到进阶功能。第一次体验不应要求用户寻找导出工具、交出私人历史或配置十几个人格参数。

星座保留为可选角色叙事标签，不进入决定行为的硬规则。角色差异主要来自当前目标、生活安排、表达习惯、边界、注意力、过去发生的事件，以及会被新证据修正的理解。单纯随机冷淡或故意制造焦虑不能作为“真人感”的验收标准。

## 2. 对旧方案的判断

9 月 4 日 v3 规格中，事件驱动、真实时间与加速时间、短中长期记忆、可追溯事实、离线补算和沉浸后复盘是正确方向，值得保留。当前仓库未出现计划中的 `crush_core`、v3 测试目录和实际 GUI；`Crush.skill/ui/*.json` 是描述文件，不是可运行界面。

建议修改旧实施顺序：第一个里程碑就交付一个薄 GUI 和一个端到端角色场景，不能先完成几十个内部模块才验证体验。对用户而言，“不会总秒回、会继续上次话题、能自然处理一次误解”比框架名称更有价值。

另外必须把动作、时间、记忆和生成放在共用核心。现在 CLI 有自己的时间线线程、JSON 状态和概率规则，skill 没有相同的自主运行宿主；“共用 runtime”并不代表两端已经具有等价行为。

补充静态发现（不要混称已经完成端到端复现）：

- **安装入口失配**：README 推荐 `curl .../2.4/scripts/install_cli.sh | bash`。已读取该远端脚本，内容依赖本地 `BASH_SOURCE[0]` 和完整源码目录，没有下载仓库/发布包的步骤。它适合作为源码安装脚本，不能直接作为远端 bootstrap；管道执行还会令脚本路径推断失效。未运行其安装/删除动作。发布验收应在全新临时目录实际跑通下载、校验、安装和启动。
- **记忆检索接线不完整**：HybridMemoryBackend 有 mem0 检索方法，但聊天上下文直接调用 SQLite 的 `build_memory_context`，没有进入 hybrid 检索；可选 mem0 写入并不等于其召回被用于回复。
- **重复信号习惯化不跨进程**：StateEngine 的历史在实例字典中。宿主每轮执行 execute.py 会创建新实例，和长期驻留 CLI 的行为不一致。
- **无统一睡眠 gate**：定时主动消息依据间隔与概率触发，没有明确角色时区、睡眠窗口和恢复队列；生成提示词代替不了调度约束。
- **失败重试重复计分**：chat 在模型回复前已经提交关系变化；现有流程缺少 request/event 幂等身份。重复发送作为重试会再计一轮。
- **配置并发写**：前台与后台直接 `write_text(config.json)`，无原子替换/状态锁；进程中断或并发读写可能丢配置，需故障注入量化。
- **“本地”表述不精确**：记录存储在本地，但被选入 runtime prompt 的风格样本、姓名/地点或媒体路径会随模型请求发往已配置服务。不能将本地存储描述成数据绝不出设备。
- **多语言/角色身份割裂**：若干提示和说明硬编码“她”和中文，provider 后置提示也固定角色口吻；复盘助手输出与该提示冲突。非女性角色、多语言和 review 必须单独验证。
- **导入文本进入系统 prompt**：历史样本与系统约束混合拼接；需测试注入文本不能改变模式、访问权限或伪造权威，当前尚未做真实模型攻击评测。

## 4. 为什么现在“不像真人”

当前普通链路是消息关键词/可选语义评分 → 数值变化 → 长提示词 → 文本回复。导入链路又绕过部分人格/状态约束。模型负责“说得像”，但没有稳定的“为什么此刻做这个动作”的共用系统。

应当同时有三类信息：世界事实（今天有安排）、角色理解（不确定对方是否忘了约定）、对外动作（先等，晚点问一次）。同一事件可改变理解，但不能凭空改变世界事实。模型生成的生活片段一经采用应进入事件记录，否则下一轮又可能另编一套。

“自我思考”实现为有触发条件的状态更新：新消息、计划到期、醒来、外部生活事件、未解决话题达到跟进窗口。后台不必每几秒调用一次模型。关闭程序期间不声称持续运行，恢复时按最后事件和时间差补算；工作和睡眠不自动变成被忽视证据。

意外感来自一致的生活和偏好：想分享的一件小事、记得未完成的话题、对一个误会保留疑问、需要时间调整情绪。不能靠固定追问“到家没”、提高随机性或任意惩罚制造。

## 5. GUI 的范围与交互方案

**决定：设计并实现本地 Web GUI，作为首个普通用户入口；同一个核心继续供 CLI 和 skill 使用。**

建议栈为 Python 核心 + FastAPI 本地服务 + React/TypeScript 界面；发送操作走 HTTP，事件流可用 SSE。这个选择用于复用现有 Python 资产和实现可恢复事件，不是已有实现。首个版本绑定本机地址、具有会话鉴权与 origin 校验；浏览器断开不应丢失已提交动作。

桌面安装器、通知、托盘与系统密钥链有明确需求后再决定 Tauri/Electron；先验证 Python 后端随包发布和升级路径。Web GUI 在后台服务退出后不会继续主动发消息；PWA 也不能自动解决桌面后台生命周期。

桌面布局建议：

```text
┌───────────────┬───────────────────────────────────┐
│ Crush         │ 角色名                  场景信息  ⋯│
│               ├───────────────────────────────────┤
│ 邂逅          │              今天                 │
│ 练习          │ 对方的消息                        │
│ 复盘          │                  自己的消息       │
│               │                                   │
│ 当前会话      │ 时间分隔 / 媒体 / 已约定事项       │
│               │                                   │
│ 设置与数据    ├───────────────────────────────────┤
│               │ ＋  输入消息                 发送 │
└───────────────┴───────────────────────────────────┘
```

右侧复盘面板仅在用户主动打开或自然检查点显示，窄屏改独立页面。不能把角色内心、后台数值或推断展示为用户在聊天中本来就知道的事实。

首个 GUI 包含五个完整页面/状态集合：

1. **开始体验**：一个可点击场景，先跑标注清楚的离线演示；自由输入需要连接模型时再引导设置。展示虚构角色、场景节奏与退出方式。
2. **聊天**：连续消息、段落、时间、媒体、历史恢复、失败消息重试、暂停与返回。状态区分“请求失败”“已排队”和角色真正发出的动作。
3. **关系事件**：只显示用户已知的约定和互动，不暴露隐藏推断。多日返回可折叠“离开期间发生的事”，禁止一次刷出大量过期追问。
4. **复盘**：选中具体一轮查看证据、多个解释、边界与替代表达；从快照尝试另一种说法，原轨迹保留。
5. **设置与数据**：provider、连接测试、语言、节奏、通知、导入预览、导出、删除范围及确认结果。技术分数和 token 放诊断折叠项。

首期不扩张到 3D 场景、多人世界、语音通话、社交社区或商城。先证明一段文字关系跨天仍可信；语音与表情包是后续增强，不能掩盖核心状态错误。

## 6. CLI、skill、视觉与动画

CLI 应升级信息结构和可靠性：聊天主区、稳定输入区、按需帮助、独立复盘；默认关闭每轮“下一句攻略”。无模型时给体验/配置选择，不向普通用户倾倒 runtime prompt。单次命令应有正确退出码，提供 JSON 输出，保证脚本调用不混入 logo 和动画。

可评估 Rich 与 prompt_toolkit 来处理中文宽度、样式和输入重绘；若需要全屏多面板才考虑 Textual。库的引入以解决已复现的问题为依据。当前手写后台 print 与 input/spinner 并存，难以稳定维护。

skill 的“UI”是宿主如何展示回复和诊断。保持一个消息动作的结构化协议，宿主以受约束的角色内容呈现；`record_reply` 需要消息 ID 和幂等性，不能只依赖宿主“如果支持就记一下”。宿主不支持后台任务时，显式提供 advance/resume 等能力，不宣称它有和 GUI 相同的自主生命周期。

视觉建议：暖白/浅灰背景，正文深灰，玫瑰色用于强调与选中态；提供深色主题。聊天正文优先可读性、中文字体、充足行高和适度气泡宽度。避免整屏仪表盘和持续漂浮装饰影响阅读。

动画规则建议：

- 消息按动作分段出现，而非把模型 token 当真人逐字输入直播；输入状态只在角色确实进入撰写阶段展示。
- 界面切换/气泡进入采用短而克制的过渡，优先 opacity/transform；跟随 reduced-motion。
- 用户正在读旧消息时不自动拉到底；显示新消息提示。图片加载预留比例，避免跳版。
- 网络加载状态和角色沉默分开。网络失败不能被包装成对方故意不回。
- 提供 320/390 像素窄屏、200% 缩放、键盘操作、emoji 和多行消息验收。

现有 README 动图并非真实界面的录像。已检查 SVG 源码与此前静态预览：CLI 动图结构检查通过，但该 Quick Look 预览只显示初始输入、消息区为空，不能证明完整动态周期都可读。hero 包含持续 CSS/SMIL 动效，没有对应 reduced-motion 规则；1200 宽画布内 16–20 像素文字缩到手机宽度后非常小。建议保留用户原有开头、结尾与动图位置，改为真实新界面的精简演示；静态兜底必须完整表达场景。尚未完成浏览器逐时刻截图验证，不能宣称动画视觉已全面通过。

## 7. 当前项目值得借鉴的部分

以下为本轮查阅官方仓库/文档后的建议；未把它们安装到本项目，也未做同模型对话横向跑分。

| 项目 | 查到的能力/状态 | 对 Crush 的具体启发 |
|---|---|---|
| [AIRI](https://github.com/moeru-ai/airi) | Web/桌面角色呈现，语音和 Live2D/VRM，模块化相关项目，区分能力与 WIP | 学习可体验入口、消息/语音/动作协调与角色存在感；文字场景先完成，避免提前承担整个虚拟人栈 |
| [SillyTavern](https://github.com/SillyTavern/SillyTavern)、[World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/) | 面向进阶用户的 LLM 前端，World Info 按条件插入上下文 | 学习角色与会话组织、可控上下文；Crush 首屏应显著少于进阶工具的参数量。仓库 AGPL-3.0，借鉴交互与直接复制代码不是同一件事 |
| [Graphiti](https://github.com/getzep/graphiti) | 增量时态事实、来源、有效期、混合检索；需要相应图后端 | 学习“过去是真的，现在不再成立”的事实管理，承诺/事件/人物关系可类型化；默认本地版本先保留 SQLite，重图后端作为选配 |
| [Letta](https://github.com/letta-ai/letta) | 当前原仓库说明旧 V1 源码已退休，指向新的 Letta Agent/SDK 路径 | 借鉴持久身份和状态管理，不能沿用旧教程直接接入已停止支持的服务；若采用需重新验证当前 SDK 与自托管方式 |
| [Generative Agents](https://github.com/joonspk-research/generative_agents) | 行为模拟、保存/恢复、分支与回放 | 学习生活计划与轨迹可回放；它是研究参考，不能把其演示或成本模型直接当成消费产品验证 |
| [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 持久化状态和 checkpoints | 借鉴恢复与分支语义；小规模本地核心先保证事务和事件幂等，复杂长流程需要时再接入 |
| [Microsoft GraphRAG](https://github.com/microsoft/graphrag) | 官方说明主要进入维护模式，并提示索引成本 | 不作为单角色持续聊天的默认记忆系统；不是“只要加图就更像人” |

GUI 技术资料：[FastAPI](https://fastapi.tiangolo.com/)、[Tauri](https://v2.tauri.app/start/)。本报告的技术组合和采用顺序是面向当前代码的工程判断，不是这些项目的效果承诺。

## 8. 记忆与 agent 架构的推荐落点

保留旧 v3 中的 SQLite 事件源方案；先做可靠召回，再考虑额外图引擎。中文全文搜索需要明确分词或 n-gram 策略，不能只换成 FTS5 后就认为中文语义检索已解决。

| 层 | 保存什么 | 读取方式 |
|---|---|---|
| 短期 | 当前对话、未回应问题、刚发生的动作 | 有序事件窗口，不做近似检索 |
| 中期 | 最近几日的计划、误解、约定和情绪余波 | 时间范围 + 全文/向量融合 + 重要性和来源过滤 |
| 长期 | 稳定偏好、关键经历、边界及其变化 | 类型化事实 + 有效期 + 源事件；冲突保留历史 |

向量是召回的一路，不管理现实真相。事件表至少区分 event time、recorded time、session、actor、来源；角色推测另存 confidence 和证据，不写成事实。导入删除需要能沿来源撤回派生记录。

动作建议用有限集合表达：等待、延迟、回复、连续消息、分享、提问、婉拒、明确拒绝、修复、结束。模型负责提出符合角色背景的判断和表达；程序验证时间、消息归属、已知事实与动作是否允许。不要把每个组件都变成独立 LLM agent。

调用预算：普通轮次从一次结构化决策/生成开始；只有复杂冲突或需要修复时增加阶段。是否值得两阶段，应做同模型消融测试；每个事件有最大调用数与超时，空闲无意义轮询不调用模型。

## 9. 实施优先级与验收

| 阶段 | 可交付结果 | 必须通过的验收 |
|---|---|---|
| A 修稳现有入口 | 安装/导入可用，消息归属正确，重复操作幂等，删除语义真实 | B01/B03/B04/B05/B06/B09/B10/B15 回归；fresh install；失败重试只落一次状态 |
| B 共用核心 + 薄 GUI | 一个 First Spark 场景同时支持 GUI/CLI/skill，消息与状态同源 | 同一事件序列得到相同核心结果；语言切换不改变角色性别；首次体验无需私人数据 |
| C 时间与记忆 | 睡眠、约定、生活事件、跨日恢复、稳定召回 | 8 小时离开不自动判忽视；过期消息不刷屏；120 条以上精确召回；承诺变更保留来源 |
| D 复盘与分支 | 一个具体事件的证据复盘与替代表达尝试 | 复盘不污染角色记忆；分支不覆盖原轨迹；解释承认歧义 |
| E 公开演示与发布 | 真实 GUI 录屏、标注演示、场景包和验证记录 | 可复现 demo；无个人隐私；CLI/GUI/skill 安装矩阵；非模拟输出不冒充跑分结果 |

评测应分开工程正确性和体验：工程用离线确定性用例；真人感用相同模型、相同场景的旧版/新版盲测，评价角色一致性、记忆正确性、节奏合理性、误解修复、重复套话率。不要用“模型觉得自己像人”作为唯一评审，也不要把几十轮集成测试通过当成人类体验已通过。

建议初期邀请约 10–15 名目标用户做探索性测试，记录第一次理解产品所需时间、是否完成首次练习、是否愿意继续、复盘是否改变了理解；样本仅作设计反馈，不宣称统计上的普遍有效。用户主观焦虑是否增加也应收集。

传播材料围绕三个真实可运行片段：隔一天仍记得一个约定；一次误解经沟通被修复；接受婉拒后体面收尾。用户分享的是合成场景或主动选择且预览过的片段。Star、社区规模和安装量另记，不能替代留存、可用性和学习价值。
