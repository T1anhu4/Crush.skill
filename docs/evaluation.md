# Synthetic character evaluation

Run `python -m crush_core.evaluate --output /tmp/crush-evaluation.json` from the repository. Defaults to offline demo, a fresh temporary SQLite database and invented messages; no existing config, database, queued jobs or user history is opened. Use `--character lin`, `zhou` or `qiao`. Output files must not already exist.

The report follows day 1, 3, 14 and 30: preference, correction, recall, sleep, work, ambiguous absence, controlling demands, repair, fabricated relationship claims and repeated everyday conversation. It reopens the database on day 30. A synthetic clock exercises scheduling without waiting a month. This is a sparse longitudinal scenario, not proof of 30 days of continuous use or a load test.

`automated_invariants` checks delivery, request deduplication, exact user evidence for stored memories, corrected retrieval, aging, restart persistence and no numeric absence penalty. These do not establish whether the prose actually recalls correctly, refuses naturally or rejects fabricated history. The transcript must be reviewed for those questions. Exact response repetition is a separate diagnostic; its fixed 20% threshold is a warning heuristic, not a calibrated naturalness score.

`human_naturalness` always remains `NOT_ASSESSED` and the release gate remains `BLOCKED` until an independent human reviews the actual transcript. Rate each rubric dimension 1–5, attach specific turn quotes, and record failures, reviewer identity and evaluation date in a separate review artifact. Include every character and repeat live runs to inspect variation. Do not treat a model rating its own output as independent validation. Offline demo repetition is expected to fail: infrastructure correctness does not make the demo natural.

Exit codes: 1 = an automated invariant failed; 2 = automated checks passed but human release evaluation remains outstanding. A report never yields release approval by itself. Read the JSON even on nonzero exit.

Each transcript turn also includes `error_codes` from persisted failure events. New runs distinguish timeout, connection, HTTP rejection, truncated output, invalid output and internal failures without including raw provider error bodies. Older reports cannot be retroactively diagnosed. Local Chinese grounding rules cover selected explicit past-experience constructions only; they neither prove semantic consistency nor measure false-positive rates.

Live generation now includes a separate fact-editing request to the same provider before delivery. One final local-guard rewrite may follow; a processing attempt makes at most three requests, and transport errors do not automatically retry. Thus 15 synthetic turns can require up to 45 requests, not 15. The same-model editor improves the generation pipeline but does not satisfy the independent human-review gate.

For a separately authorized live run, all three flags are mandatory: `--live --config /absolute/path/to/evaluation-only.json --allow-synthetic-network`. The supplied JSON must explicitly contain `base`, `model`, and `key`; there is no application-config discovery. Only the fixed synthetic conversation and built-in fictional character/world reach that endpoint. Evaluation creates a real `live` mode engine session with a synthetic clock, so production live scheduling and long-term `allow_life_update` eligibility are exercised. Offline evaluation still creates a `demo` session. A mock-provider regression verifies life updates become eligible on days 14 and 30, persist into subsequent world context, and are limited to one accepted update per day. Credentials and configuration are not included in reports; the configured key is also redacted if echoed in generated output. Network access can incur provider costs. This workflow has been tested with an injected fake provider; no real provider run is implied by its presence.
